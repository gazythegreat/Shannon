# Shannon — Your whole second brain, in a fraction of the space.

*Named for Claude E. Shannon: the method stores the surprise — the delta in meaning — and points at the rest.*

**Your whole second brain, in a fraction of the space.** Search a large document store through a small, standing **abstract map** — never through a copy of the store. The map holds, per source: one short abstract (lossy, plain language), its **Keys** verbatim (lossless: identifiers, amounts, deadlines), its entities, and a **pointer** to the original. Sources are never copied into the map. Exact wording is fetched live from the original, singly, only when a question needs it. There are no embeddings, no vector store, no text database.

The method is domain-free. Everything domain-specific lives in a **deployment pack**: what counts as a Key, the layer vocabulary, the store root, the tag vocabulary, a typed lay↔technical thesaurus, and a house-terms register. A law firm and a logistics firm run the same procedure with different packs.

## Custody of the map — the user's copy comes first

**A copy of the map must be kept in the user's own custody. This is a standing rule of the method, not a deployment preference. It must be stated to the user explicitly — highlighted, never buried — before the first build, and again whenever custody changes.**

The map is the user's second brain in miniature: for every source an abstract, its Keys and a pointer, in one small file set. Where that file set lives is a custody decision about the user's own information. The default is the user's own machine, or storage under the user's control. The deployment pack records where the user's copy lives, and every build or refresh leaves that copy current — or says plainly why it could not be updated.

The agent's machine (the VM or host the agent runs on) may hold the working copy the skill searches over. A deployment may let the agent's machine be the map's only home **only on the user's express choice, made after the repercussions have been stated to the user plainly:**

- **Loss.** The agent's machine is outside the user's control: it can be replaced, reset, suspended or terminated by whoever operates it, and a map that exists only there goes with it. A copy in the user's custody survives all of that and can always be re-adopted (see Detection & adoption).
- **Confidentiality.** The map concentrates the store's skeleton — every abstract, identifier, amount and deadline — into a fraction of the space. That concentration is the method's point, and it is exactly why custody matters: whoever holds the only copy holds the shape of the whole store.
- **Access.** A copy on the agent's machine is reachable only through that agent and that service. The user's own copy is theirs to open, back up, move and keep, with no intermediary.

Until that express choice is recorded in the deployment pack — the choice, its date, and that the repercussions above were stated — a build or refresh that leaves the only copy on the agent's machine is **incomplete**, and the run must say so.

## Two modes

This skill has two modes. **Build mode** cards sources into a map (see the card spec below); **search mode** runs the procedure over a finished map. Search mode has one visual presentation option, **Shannon 3D** (see its section below): on the trigger "Shannon 3d <subject>" it renders the search traversal for that subject as an interactive 3D graph in HTML, with visible lines between nodes. Detection comes first, always: search mode checks for an existing map before anything else, and build mode never re-cards what a current map already covers — it refreshes changed sources only. The skill is self-sufficient end to end: a deployment with no upstream indexes at all still has a complete path, because build mode can card primary sources directly. Upstream producers (audit skills, transcript reconcilers, human-maintained hubs) are accelerators that give build mode better raw material; they are never prerequisites. "Indexing" in this skill means carding — abstracting into the map. It never means duplicating text into a database or vector store.

## Step 0 — Derive the frame (before any build, and whenever a deployment starts)

A delta exists only under a frame: a stipulated answer to *what counts as a change*. The mathematics cannot supply the frame (Bertrand's paradox, Goodman's grue, Watanabe's ugly duckling theorem, Tishby's relevance variable all end at the same place). The frame is therefore **derived from the record first**: from what the user has actually done, chased, corrected, preserved and let drop, across their store and their history with the system. Asking is permitted — and often the fastest way to settle a line the record leaves open — especially where the user wishes to give an answer, and preferably on the system's initiative: the model asks, drawing its questions from what the record already shows, rather than waiting to be told. But an answer is evidence of the stated tier, not the revealed: a question whose honest answer costs the answerer something — *are you aware of the frame you impose? what do you really pay attention to?* — tends to return the free answer, so on exactly the points that matter self-report is weighted accordingly. The tiering is the profiler's: stated < revealed. A frame line resting only on the user's description of themself is a stated-tier claim and cannot stand alone — it stands as STATED until behaviour confirms it, and the delta log arbitrates it like any other line. The method is for **anyone organising their own information, in any field or none**; law is one deployment pack among many, never the assumption.

Derive, in this order:

1. **Area and macro environment — from the store itself.** What the store actually contains, and what the user actually does with it, names the area more honestly than any answer: a corpus of pleadings, transcripts and deadlines is a litigation deployment whether or not the user would call it one; a store of plans, commitments, preferences and family documents is a general one. Logistics facts that leave no behavioural trace — where the store root is, who else touches it, what may never leave the machine — may be asked outright: they are facts, not self-assessments, and cannot be profitably faked.
2. **Axes — from revealed attention.** What counts as a change for this user is what they have historically treated as one: the discrepancies they corrected, the movements they chased within a day, the conflicts they insisted on preserving unsmoothed, the figures they would not let stand rounded, the failure modes they made the system tag. Read the corrections and the follow-ups first — they are the axes with their evidence already attached.
3. **Holders — from the record.** The people and bodies whose movements the user's history actually tracks (parties, counterparties, a court, the user themself) — not the ones a questionnaire would nominate.
4. **Present for recognition, not report.** Show the user the derived frame with a pointer to the evidence under each line. Recognition is far harder to fake than self-description — the same reason the search procedure answers lay questions with a candidate set to recognise rather than jargon to recall. The user corrects what the record got wrong; each correction is itself behavioural evidence and is logged as such. A frame line the user merely asserts, against the record or without it, is marked STATED and carries the lowest weight until behaviour confirms it. Where the record leaves a line genuinely open, ask it outright at this point: an answer the user wishes to give, marked STATED, is better than a silent guess.

Then **counterweight with the market frame.** The derived frame still carries the user's cognitive biases — visible in the record itself once you look: recency (the latest movement overweighted), salience (dramatic reversals noticed, slow drift missed), confirmation (changes that fit the user's theory chased, others let drop), and small-sample certainty (one career's worth of cases mistaken for the field's base rates). The model, having read the field's literature at scale, usually knows things the individual cannot: the field's base rates, which signals conventionally precede real movement and which are noise or posture, how often a declared position is executed on, and the typical causes behind an observed change (including procedural compulsion, which looks like a change of mind and is not). So present the market frame for the derived area — its standard change-events, signal-versus-noise conventions and base rates — as **PROPOSED** entries beside the derived ones, and flag every divergence explicitly. Neither side overrides silently: the record disposes on local evidence (this store, this lingo, these counterparties); the market frame earns its place only as confirmed entries.

Record the outcome as the deployment's **frame**: area, environment, axes, holders, change-event vocabulary — each line marked derived (with its evidence pointer), market-proposed, user-confirmed, or stated-unconfirmed, and versioned additively as it changes. If there is no record yet to derive from (a genuinely new user), run on the market frame alone, fully PROPOSED, plus the logistics facts, and say so wherever a delta is reported; an underived frame must never wear a derived frame's confidence. Derivation is a standing duty, repeated as the record grows — and the recorded delta log is the long-run arbiter between the derived frame and the market's: periodically check which proposed change-events actually preceded real movements in this store, and let that record argue for promotion or demotion of frame entries.

**The two mapping criteria.** Everything the map treats as worth recording — and every delta it will ever report — is governed by criteria from exactly two sources, and the frame records which source each criterion came from. **(1) The market criteria:** what the field or context the owner operates in conventionally treats as a real change — its standard change-events, base rates and signal-versus-noise conventions — supplied by the model from the field's literature, and held as PROPOSED until the owner's record confirms them. **(2) The owner's criteria:** the objectives and change-definitions revealed in the owner's own record — their documents, logs and chat history: what they have historically chased, corrected, refused to let stand rounded, or insisted on keeping distinct. This source exposes the owner's biases in the record itself. The owner may also state their criteria directly: the system may ask — preferably on its own initiative, where the record leaves a line open — and an answer the owner wishes to give is welcomed. Stated criteria enter at the stated tier, weighted as the least reliable evidence until behaviour confirms them; each derived criterion carries its evidence pointer, so the bias is visible, not hidden. Neither source alone is sufficient: market criteria without the owner's record produce a generic map of someone else's priorities, and the owner's criteria without the market counterweight entrench their blind spots as method. Where the two diverge, the divergence is flagged in the frame, and the delta log arbitrates over time. The criteria are applied together, per card — every card stores both readings side by side (see the card spec), never one instead of the other.

## The artefacts

1. **The map** — three levels. *Atlas* (top: one entry per cluster; small enough to load whole, ~5k tokens) → *cluster summaries* → *cards* (one per source). Connections are **not stored as edges**: they are derived at query time by joining on shared field values (Cluster, Keys, Entities, Tags, Date) — the way a relational join derives a graph from tables.
2. **The registry / dimension table** — the deployment's canonical list of the things questions are about (in a law practice, a matter registry; in a research corpus, a bibliography of works). It resolves any fragment — a name, a topic, a figure — to the clean key the cards join on.
3. **The thesaurus** — typed keyword relationships for the domain: lay↔technical pairs, hypernym families, and **siblings with their distinctions spelled out** (expansion uses the family; the answer must keep siblings separate). Every entry is marked AI-proposed or confirmed.
4. **The house-terms register** — the organisation's private vocabulary: nicknames, codenames, inside jokes, catchphrase-rules. Each entry: term → referent → type (person / matter / rule) → status (proposed / confirmed) → pointer to where it was explained or first used. AI may *propose* entries from recurrence patterns; only an insider confirms. A wrong house-term edge silently corrupts searches, so unconfirmed entries are used as hints, never as facts.
5. **The position & delta register** — the deployment's record of *meaning in motion*, under the frame stipulated at Step 0. For each holder and axis: the current position (a stance, an opinion, a plan), stated as a proposition; its **evidential basis** — the support under it (documents, testimony, data, commitments) as pointers; and a dated **delta log**. A delta record states: axis · holder · from → to · **direction** (toward / away / hardened / softened / reversed / basis-strengthened / basis-weakened) · **what moved** (the position's wording, the basis, or both — a basis that shifts under unchanged wording is a full delta; a wording that shifts over an unchanged basis is recorded as a rephrase, delta nil) · date · source pointer. Positions are never overwritten: a new position supersedes the old in the log, additively, so the history is the register.
6. **The trend roll-up** — periodically (and on request), the delta log is read as a time series per holder and axis: trajectory (steady drift, oscillation, sudden reversal, long stillness), rate of movement, and divergence between holders. Trends are second-order deltas — they answer "how has this been moving?" rather than "where does it stand?" — and they are the counterweight to salience and recency bias: slow drift that no single source announces becomes visible only here. A trend is a reading of the log, labelled with the period it covers; it is never a source, and any trend that matters is verified against the delta records under it.

## The search procedure

Run these steps in order. The intelligence lives here, in the procedure — the map is inert data.

1. **House terms first.** Check the question against the register before any ordinary reading. A house term overrides the word's normal meaning ("the Falcon" is a person, not a bird).
2. **Resolve.** If the question carries a fragment (name, topic, figure), resolve it through the registry to its canonical key(s) before probing. Never search on the raw fragment alone.
3. **Interpret.** Parse the question — especially a lay one — into an event schema: actor, action, subject, effect, time anchor. A lay question ("the judge told my aunt she cannot continue the proceeding") shares almost no vocabulary with the documents; the schema is the bridge.
4. **Expand.** Turn the schema into the deployment's technical vocabulary using the thesaurus — the *whole family* (striking out / struck out / dismissed / discontinuance / unless order / case terminated), not one guessed term. For public domains the searching model may extend the family from its own knowledge; mark any term so added as unconfirmed.
5. **Probe the map mechanically.** Order: Keys (exact) → Entities → Abstracts → Answers lines. Abstracts describe outcomes in narrative words, which sit closer to lay vocabulary than procedural labels do. Use `map_query.py` (in the map directory) so the probing is grep, not impression: `map_query.py <terms...> [--field keys|entities|abstract|answers]`, and `--join "<value>"` to pull every card sharing a key or entity. **Sibling maps are probed together**: where the deployment pack registers sibling maps (see "Sibling maps" below), pass them all — `--map <dir1>,<dir2>,...` — and the probe searches every map in one pass, labelling each hit with the map it came from. A question is not answered from one map while a registered sibling that covers the same subject sits unprobed.
6. **Traverse.** From any one hit, join outward: same key in other layers, same entity in other clusters, same cluster, adjacent dates. A faint-memory question needs only **one hook anywhere in the neighbourhood**; the joins do the rest.
7. **Drill down only for exactness.** If the answer turns on exact wording, a precise time, or a figure the cards flag as uncertain, or if the answer will be relied on in a filing, a decision or advice, follow the card's Source pointer and fetch that one original, live. If a card's abstract records a correction or a conflict, the drill-down is mandatory before answering.
8. **Abstain and widen.** If the map yields nothing, say so: an empty result is not an answer. Search the originals with the expanded term family AND with terms taken directly from the question, without confining the search to the map's folders, clusters or keys. Never invent an answer the map does not support; never smooth a conflict the cards preserve. See "The map leads; it does not limit".
9. **Answer in the asker's register.** For a lay asker, return a small candidate set described plainly, with the sibling distinctions spelled out — converting recall (produce the jargon) into recognition (pick from plain descriptions). For an expert asker, lead with keys and pointers.

### Change questions

A question of the form "what changed about X?", "how has Y's position moved?", "is Z's case stronger than it was?" is answered from the **position & delta register first** — that is what it exists for. Procedure: resolve the holder and axis through the registry and frame; read the delta log for that pair in date order; state the current position, then the movements with their dates, directions and what moved (position, basis, or both), each with its source pointer; close with the trend reading if the log supports one. If the frame was never stipulated, or the axis is not in the frame, say so before answering — a delta reported without its frame is a number without a unit. If the register holds no record for the pair, abstain and fall back to the ordinary probe across dated cards, labelling the result as reconstructed-at-query-time rather than recorded.

## The map leads; it does not limit

The map decides where to look first. It never decides where not to look.

| Map result | Status |
|---|---|
| Nothing found | Never conclusive. Run an independent search. |
| A hit not yet checked in the original | A lead, not a finding. |
| A hit confirmed in the original | Conclusive for that fact only. |
| Anything a filing, a decision or advice will rely on | Search independently as well, whatever the map returned. |

Rules:
1. Independent searches use terms taken from the question and from the source documents themselves, not only the map's term family, house terms or thesaurus.
2. Independent searches are not confined to the folders, clusters or keys the map points to.
3. Anything newer than the last refresh is searched directly. Check the manifest date before relying on the map for recent material.
4. Searches outside the store (court databases, the web, law reports) are never displaced by the map.
5. When an answer rests on the map, say so and say which result row above applies.

## If a Shannon map already exists — adopt it, do not rebuild

Detection is wider than the pack's configured location. Before any build, look for an existing Shannon map: in the location the deployment pack names; elsewhere in the store (a map is recognisable by its signature — an atlas, cluster summaries, card files and a build manifest together); and in any copy the owner points to. If one is found, **adopt it**: read its atlas first, check its manifest against the store to establish what it already covers and how stale it is, record the adoption in the deployment pack (where the map was found, its coverage, its manifest state), and continue from it — search mode runs over it immediately, and build mode refreshes only the delta between its manifest and the store's current state. Never re-card from scratch what a sound existing map already covers: re-carding identical sources produces a second, divergent map where one would do. If several maps or copies exist, treat them as copies of one map, not rivals: the deployment pack states which copy is the master; work from the master, flag any copy that has diverged from it, and never merge two maps silently — surface the divergence to the owner. Only when no existing map is found anywhere does the fallback below apply.

## Sibling maps — a second map beside the first (added 24 Nov 2026)

A deployment may hold more than one map. Two different things must not be confused:

- **Copies of one map** — the same map in several places (master, mirror, case-local exports). One is the master; the rest are copies. The adoption rule above governs them: never merge two copies silently, never treat a copy as a rival.
- **Sibling maps** — genuinely different maps that sit beside each other: a frame-specific or subject-specific map built over a subset (or a re-framing) of the store, with its own cards, its own register axes, and its own manifest, while the general map continues beside it. A sibling is not a copy and not a rival: it answers a different question about overlapping material. Building one is legitimate where a new frame (Step 0) would distort the general map if forced into it — the sibling carries the frame; the general map stays frame-neutral.

Rules for siblings:

1. **Registered, never ambient.** Every sibling is named in the deployment pack: its location, its subject or frame, its build date and provenance, and its custody copy (the custody rule applies to siblings exactly as to the master).
2. **Searched together.** Search mode probes the master and every registered sibling that covers the question's subject, in one pass (`map_query.py --map <dir1>,<dir2>`), and the answer names which map each hit came from. A card that exists in both maps is reported once, from the sibling if the question is in the sibling's frame, else from the master — never double-counted as two sources.
3. **Extracts are labelled.** Cards a sibling takes from the master are extracts, marked as such in the sibling's manifest; the master's text governs if the two ever diverge, and the divergence is surfaced, never silently resolved.
4. **Registers stay separate.** A sibling's position & delta register holds its own axes. The master's register is not edited by a sibling build; a frame that later proves general is promoted into the master only on the deployment owner's direction, as a recorded promotion, not a merge.
5. **Case-local exports follow the map that covers the matter.** Where a sibling covers a subject, that subject's case-local export is re-exported from the sibling, and the export's manifest says which map it came from.

## When no map is detected — the fallback

Detection: look for the deployment's map at its configured location — atlas, cluster summaries and cards. Absent, empty or unreadable all count as **no map**; there is no partial credit. Then:

1. **Declare it.** Tell the user, in the answer itself, that no map was found and where the skill looked. An unmapped answer must never wear a mapped answer's confidence.
2. **Degrade in declared tiers**, naming the tier in use:
   - *Tier 1* — probe the store's native finding aids directly (folder indexes, hubs, the registry), if they exist;
   - *Tier 2* — exact-word grep over the originals in place, using the expanded term family, scoped by the store's folder structure — naming the expected cost before any large sweep;
   - *Tier 3* — memory only, labelled as memory, with the capture caveat attached (memory returns only what past work happened to record).
3. **Offer the remedy; never take it silently.** Propose build mode — sources counted, cost stated — and build only on the deployment owner's go-ahead. A missing map is not a licence to spend tokens uninvited.
4. **Log the miss.** Record in the deployment's notes that a search ran unmapped, so the gap stays auditable rather than evaporating.
5. **Never fabricate.** If every tier fails, abstain and say what would be needed (a map build, or a pointer to the right store).

## Card spec (for building or refreshing a map)

One card per source, fixed schema: Title / Source (pointer, relative to the store root, stated once per file) / Layer / Date / Cluster / Abstract (40–55 words, abstracted — never copied sentences; ambiguity and self-contradiction flagged, never smoothed) / Market proposition (one line — the reading under the market criteria) / Owner proposition (one line — the reading under the owner's criteria) / Keys (verbatim, semicolon-separated; **Keys outrank any size target**; personal identifiers such as NRICs never go in Keys) / Entities (including nicknames and house terms exactly as heard — a 55-word abstract will drop them, and the register alone cannot be searched by entity joins) / Tags (only the deployment's controlled vocabulary, and only when literally present) / Answers (one line: the questions this source can answer). Cluster summaries (80–150 words per cluster) roll cards up; the atlas rolls summaries up. Card a changed source again when it changes; the map is append-and-correct, never delete (per the deployment's records rules).

**Two propositions in every card — never either/or.** The two mapping criteria are applied together at carding time, and both readings are stored in the same card. **Market proposition** (one line): the proposition the market frame takes this source to establish or move, resting on a named frame entry, marked market-proposed or confirmed. **Owner proposition** (one line): the proposition under the owner's frame — what this source establishes or moves for this owner: their objective, position, exposure or standing concern — marked derived (with its evidence pointer), stated, or user-confirmed. Both fields are mandatory. Where a frame yields no movement, the field says so expressly ("No movement under this frame") — an omitted field is a defective card, not a neutral one. The two readings may agree, diverge, or move independently; a divergence on the same card is itself a finding and is preserved, never resolved by dropping one side. Propositions are readings under a frame, not source content: they never enter Keys, are never quoted as the source's own words, and the Abstract stays source-faithful regardless of either reading.

## Refresh — keeping the map current (build mode, delta form)

A refresh never rebuilds. Procedure:

1. **Detect the delta.** Compare the store's source sets against the build manifest: files that are new, and files whose size or modification time changed since they were carded. If the store is unreachable, stop, log the skip, and change nothing.
2. **Card only the delta**, to the same card spec. New sources get new cards (appended as a dated refresh batch). For a changed source, write a NEW card and mark the old card "[Superseded — see refresh of <date>]" — corrections are additive; nothing is deleted or silently overwritten.
3. **Roll up only what the delta touched**: append a dated addendum to the affected cluster summaries; re-distil the atlas only when a cluster's posture or hardest deadline actually changed.
4. **Update the manifest** with the new entries and watermarks, and log the run: sources added, sources re-carded, map size before and after. A run with no delta reports nothing.
5. **Record the semantic deltas.** Where a deployment keeps a position & delta register (artefact 5), compare each newly carded source against the register's current positions for every holder and axis it touches. Where the source moves a position — or moves the evidential basis under an unmoved position — append a delta record (from → to, direction, what moved, date, pointer to the new card). Where the source's wording differs from a registered position but its basis does not, record nothing and note the rephrase in the run log only. A refresh that finds file deltas but no position deltas says so; the absence of movement is itself a reading, and the trend layer depends on stillness being recorded honestly rather than passed over.
6. Upstream freshness is inherited, never manufactured: a folder layer whose producer (e.g. an audit) has not re-run simply produces no delta — the refresh must not card around a stale producer to disguise that.

## Shannon 3D — graph view (presentation option, added in v1.5)

Search mode has one visual presentation option: a 3D graph of a subject, in the manner of Obsidian's 3D graph view of a vault — nodes floating in 3D space, joined by **visible lines between nodes**. It is a *view* over the existing map, never a new store: it cards nothing, stores no edges, and writes nothing back into the map. This is the map's standing principle rendered — connections are not stored as edges; they are derived at query time by joining on shared field values. The 3D graph is that derivation, drawn.

**Trigger.** The user says **"Shannon 3d"** (any capitalisation) **followed by a subject** — a matter, a person, a topic, a figure: e.g. `Shannon 3d the Meridian contract`, `Shannon 3d Jane Smith`, `Shannon 3d clause 6`. With no subject, graph the whole map at cluster level only (atlas + cluster summaries as nodes), and say that is what was done. The trigger always means: generate the HTML graph for that subject and hand it over in the reply — not a description of a graph, the file itself.

**Procedure.**

1. **Resolve and probe exactly as search mode does** (house terms → registry resolve → interpret → expand → `map_query.py` probe → traverse). The graph's scope is the traversal result: the resolved subject's cards plus everything joined to them.
2. **Nodes.** Primary nodes are the in-scope **cards** (one per source). Secondary nodes are the shared values the joins run on: **clusters, entities, holders** (from the position & delta register), and **keys** where a key is shared by two or more cards. Node size scales with degree (how many lines meet there); node colour is by layer for cards and by kind for secondary nodes, with a legend on the page.
3. **Lines between nodes — the point of the view.** Every line is one derived join, drawn visibly (a rendered line, never an implied or hover-only connection), and typed: `same-cluster` · `shared-key` · `shared-entity` · `shared-tag` · `holder-axis` (a register position/delta link) · `supersedes` (an old card to its refresh card). Hovering or selecting a line shows its type and the exact shared value it rests on. A line that cannot name its shared value is not drawn — no decorative edges, no inferred relationships.
4. **Granularity guard.** Default scope is the subject plus its 1-hop joins. Extend to 2 hops only while the result stays readable (about 300 nodes); beyond that, collapse to cluster-level nodes and state the collapse on the page. Node and line counts are printed in the page header — a graph that hides its denominator is the visual form of a false index.
5. **Output — one HTML file.** A single dated HTML file, `views/shannon-3d-<subject-slug>-<yyyymmdd>.html` in the deployment's map directory (created if absent; dated, never overwritten — corrections are additive, as everywhere in this skill). It renders with a 3D force-graph library (3d-force-graph / Three.js): rotate, zoom and pan; hover highlights a node, its neighbours and their lines; clicking a node opens a detail panel carrying that card's title, abstract, Keys, layer, date and **Source pointer** (the drill-down path to the original — the graph never replaces it). A search/filter box and the legend are on the page. If the library CDN is unreachable in the viewing environment, the file must still open and say so plainly rather than render blank.
6. **Freshness is inherited, never manufactured.** The header states the map's manifest date and, where the subject's upstream producer (e.g. an audit) is stale for in-scope sources, a banner says so — the same rule as Refresh step 6. Never card, re-card or refresh solely to make a graph look current; offer the refresh instead.
7. **Status of the artefact.** The graph is a finding aid, like the index: it is not evidence of what any source says, it proves no relationship beyond the named shared value on each line, and it is never filed, served or quoted as a record. Say so in the page footer.

## Deployment pack — what one contains

The method ships without a pack; every deployment writes its own, and a real pack is **private to its owner** — it describes their store, their vocabulary and their frame, and is never published with the method. A pack records:

- **Store root** — where the originals live (the custodian is the owner's own disk or store; the map never holds the text).
- **Map location** — where the atlas, cluster summaries, cards and probe script live.
- **Map custody** — where the user's own copy of the map lives (see Custody of the map), and whether the user has expressly chosen agent-machine-only storage: the choice, its date, and that the repercussions were stated.
- **Registry** — the canonical list the resolve step joins on, and its primary key.
- **Layers** — the kinds of sources in the store (hubs, indexes, logs, transcripts, records...).
- **Tags** — the deployment's controlled vocabulary, if any.
- **Thesaurus** — the typed lay↔technical file for the field (or the general pack).
- **House terms** — the private-vocabulary register file.
- **Frame** — the Step 0 derivation: area, environment, axes, holders, change-event vocabulary, each line marked derived / market-proposed / user-confirmed / stated-unconfirmed.
- **Position & delta register** — where artefact 5 lives, once seeded.
- **Refresh cadence** — how often the Refresh procedure runs, and where it reports.

## Growing the pack

Every search that succeeds through an unexpected word, and every correction from the asker, is a candidate thesaurus edge or house-term entry: record it as *proposed* with its source pointer, and promote to *confirmed* only on the deployment owner's word. Keep both files small and high-precision — a few hundred verified edges outperform a large auto-generated ontology, which decays into plausible noise and wrong distinctions.

## Version history

- **v1.8 — 27 Nov 2026.** The map leads; it does not limit: a new section fixes the status of every map result — an empty result is never conclusive, a hit not yet checked in the original is a lead not a finding, a hit confirmed in the original is conclusive for that fact only, and anything a filing, a decision or advice will rely on is searched independently as well, whatever the map returned. Step 8 becomes "Abstain and widen": on an empty result, search the originals with the expanded term family AND with terms taken directly from the question, without confining the search to the map's folders, clusters or keys. Step 7's drill-down now also triggers when the answer will be relied on in a filing, a decision or advice.
- **v1.7 — 24 Nov 2026.** Sibling maps: a deployment may hold a frame-specific or subject-specific map beside the general map — registered in the deployment pack, with its own cards, register axes and manifest — instead of forcing a new frame into the general map. Search probes the master and every registered sibling covering the subject in one pass (`map_query.py --map <dir1>,<dir2>`), hits labelled by map, shared cards never double-counted; registers stay separate, and a frame is promoted into the master only on the owner's direction, as a recorded promotion, not a merge.
- **v1.6 — 24 Nov 2026.** Custody of the map: a copy of the map must be kept in the user's own custody, stated to the user explicitly as a standing rule of the method. Agent-machine (VM) storage as the map's only home is permitted only on the user's express choice, after the repercussions — loss, confidentiality, access — have been stated plainly; until that choice is recorded in the deployment pack, a run that leaves the only copy on the agent's machine is incomplete.
- **v1.5 — 17 Nov 2026.** Shannon 3D: search mode gains a visual presentation option — on the trigger "Shannon 3d <subject>", the search traversal for that subject is rendered as an interactive 3D graph in a single HTML file (Obsidian-style: nodes joined by visible lines, every line one derived join typed by its shared value; click a node for its card abstract and Source pointer). The graph is a view over the map, never a store: it cards nothing, stores no edges, and inherits the map's freshness.
- **v1.4 — 14 Nov 2026.** Dual propositions per card: every card now stores both readings at the same time — the market proposition and the owner proposition — never either/or. Both fields are mandatory; "no movement under this frame" is recorded expressly rather than omitted, and a divergence between the two readings on one card is preserved as a finding.
- **v1.3 — 14 Nov 2026.** Step 0 refined: asking is permitted where the user wishes to give an answer, preferably on the system's initiative; answers are weighted at the stated tier, and derivation from the record stays primary.
- **v1.2 — 14 Nov 2026.** Existing-map adoption: a Shannon map already present is adopted and refreshed, never rebuilt ("adopt it, do not rebuild"). The two mapping criteria — the market criteria and the owner's revealed criteria — are named explicitly in Step 0.
- **v1.1 — 11 Nov 2026.** Licence changed to the PolyForm Noncommercial License 1.0.0: noncommercial use is free; any commercial use requires a paid licence from the copyright holder in advance, no exceptions. (The v1.0 dual-licence wording was withdrawn.)
- **v1.0 — 11 Nov 2026.** Initial public release.
